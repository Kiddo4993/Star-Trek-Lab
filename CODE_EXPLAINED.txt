STAR TREK LAB: HOW THE CODE WORKS
=================================

A red-matter probe is dropped 2.00e6 m above a hole drilled to the centre
of Vulcan. The site works out how long it takes to reach the centre
(1.36e3 s) and how many Vulcans per second that is (5.15e6), two ways:
step by step with Euler's method, and with the exact formulas. Then it
draws everything.


1. WHERE EVERYTHING IS
----------------------

  src/lib/physics.ts        ALL the physics. No React, no imports.
  src/lib/format.ts         Rounds numbers to 3 significant figures.
  src/lib/theme.ts          Pen colours for the graphs.
  src/lib/fonts.ts          The handwriting font (Kalam).
  src/lib/timeline.ts       Shared "where are we in the fall?" store.

  src/app/page.tsx          The page. Just shows <Lab />.
  src/app/layout.tsx        The <html> wrapper: title, font.
  src/app/globals.css       All the styling (graph paper, tape, pens).
  src/app/icon.svg          The browser-tab icon.

  src/components/Lab.tsx           The whole page: inputs, results, graphs.
  src/components/CrossSection.tsx  The animated drawing of Vulcan.
  src/components/Charts.tsx        One reusable graph ("taped-in printout").
  src/components/Scrub.tsx         A number in a sentence you drag to change.

  scripts/verify.mjs        Checks the answers are 1.36e3 s and 5.15e6.
  next.config.ts            Makes the site a plain static website.
  .github/workflows/deploy.yml   Publishes to GitHub Pages on every push.

The important idea: physics.ts knows nothing about the website, and the
website never does physics itself. It just calls physics.ts and draws the
numbers. That's why the same file can be checked by verify.mjs with no
browser at all.


2. THE PHYSICS (src/lib/physics.ts)
-----------------------------------

Sign convention, used everywhere:
  r = distance from Vulcan's centre (m)
  v = speed TOWARD the centre (m/s), positive while falling in
  a = acceleration TOWARD the centre (m/s^2)

Because v points inward, r goes DOWN as the probe falls. That's why the
position update is r -= v*dt rather than r += v*dt.

--- Constants ---
  G0 = 13.73, R = 6.792e6, POPULATION = 7.00e9 come straight from the
  question. GM is worked out from them: at the surface g0 = GM/R^2, so
  GM = g0 * R^2. DT = 0.01 s is the Euler time step.

  The drag numbers (mass 2000 kg, Cd 0.47, air 1.2*e^(-h/8500)) are also
  from the question. PROBE_RADIUS = 0.5 m is an ASSUMPTION: the question
  gives the mass but not the size, and drag needs the area A = pi*r^2.

--- gravity(r, interior) ---
  Outside (r >= R):  g = GM / r^2            (Newton)
  Inside, uniform:   g = G0 * r / R          (shell theorem: only mass
                                              closer than r pulls, and
                                              that grows like r^3)
  Inside, dense core: g = G0                  (all the mass is at the
                                              middle, so g stays 13.73)

--- airDensity(h) ---
  h is height above the surface (negative = in the shaft).
  Above ground: 1.2 * e^(-h/8500).
  Inside the shaft: THIS IS THE TODO FOR YOU. Carrying on with the same
  formula underground gives e^(+799) at the centre, which is Infinity on
  a computer. Right now it just returns sea-level air (1.2).

--- dragAccel(r, v) and netAccel(r, v, interior, drag) ---
  Drag force F = 1/2 * rho * Cd * A * v^2. Divide by mass to get an
  acceleration. Drag always fights the motion, so
      net acceleration = gravity - sign(v) * drag.
  With drag switched off it's just gravity.

--- simulate(options): EULER'S METHOD ---
  Start: r = R + dropHeight, v = launchSpeed, step = 0.
  Loop while r > 0:
      a = netAccel(r, v)      1. acceleration from where it is now
      v = v + a*dt            2. update the velocity
      r = r - v*dt            3. move, using the NEW velocity
      step = step + 1
  Total time = step * dt. (Multiplying at the end, instead of adding 0.01
  over and over, avoids tiny rounding errors piling up.)

  Using the NEW v in step 3 makes this "semi-implicit Euler" (also called
  Euler-Cromer). It's much more stable than plain Euler for the
  spring-like motion inside the planet. That's why it agrees with the
  exact answer to about 0.0003 %.

  While looping it also:
    - notes the moment r first drops below R (the surface crossing) and
      the speed at that moment;
    - saves a "sample" {t, r, v, a, x} every 1 s of simulated time, which
      the graphs and animation use (x = distance fallen = r0 - r);
    - stops anyway after 200 000 s, so a bad setting can't freeze the page.

  It returns the samples plus totalTime, surfaceTime, surfaceSpeed,
  finalSpeed and rate = POPULATION / totalTime.

--- exactSolution(dropHeight, launchSpeed, interior): THE CHECK ---
  Surface speed, from energy conservation:
      vs^2 = v0^2 + 2GM(1/R - 1/r0)

  t1 (outside), the given formula:
      t1 = sqrt(r0^3 / 2GM) * [ sqrt(x(1-x)) + acos(sqrt x) ],  x = R/r0
  This formula only works for a drop FROM REST. To handle the
  launch-speed slider, the code pretends the probe was dropped from rest
  at a higher point rA, high enough that it would already be going at v0
  when it passes r0 (from energy: 1/rA = 1/r0 - v0^2/2GM). Then
      t1 = (time from rA down to R) - (time from rA down to r0).
  With v0 = 0, rA = r0 and this is exactly the textbook formula. If v0 is
  above escape speed there is no such rA, so t1 shows as "—".

  t2 (inside):
    uniform:    inside, g is proportional to r, so the motion is simple
                harmonic, like a mass on a spring, with w = sqrt(g0/R).
                It reaches the centre when tan(w*t) = w*R/vs, so
                t2 = atan(w*R/vs) / w.
    dense core: constant g, so use the SUVAT equation R = vs*t + 1/2*g0*t^2
                and solve the quadratic:
                t2 = (-vs + sqrt(vs^2 + 2*g0*R)) / g0.

  The exact formulas ignore drag, so with drag on the "diff." column
  shows how much difference drag makes.

--- rateVsHeight(...) ---
  Runs the whole simulation 41 times (0, 250, 500 ... 10 000 km) to draw
  the rate vs height graph. It uses dt = 0.05 s instead of 0.01 s because
  that's 41 full runs; the answer changes by far less than 0.1 %.

--- thin(list, max) ---
  A fall can have thousands of samples. Graphs only need about 600 points,
  so this keeps every k-th one (and always the last one).


3. ROUNDING (src/lib/format.ts)
-------------------------------
  sf3(x): x.toPrecision(3) gives "1.36e+3"; this turns it into
          "1.36 × 10³". Every number shown on the page goes through it.
  tick(x): short axis labels like 12k or 5M.


4. THE PAGE (src/components/Lab.tsx)
------------------------------------
  State: four useState values, one for each control (heightKm,
  launchSpeed, interior, drag).

  useDeferredValue: dragging a slider changes the value many times a
  second, and each change re-runs several simulations. Deferring lets the
  slider keep moving smoothly while the maths catches up; "working it
  out…" shows while it's behind.

  useMemo: each calculation only re-runs when its own inputs change:
    sim         the main Euler run (dt = 0.01 s)
    exact       the formulas
    plotData    sim samples thinned for the graphs
    comparison  four extra runs: uniform/dense core × drag off/on
    gSeries     g at 301 distances, for both interior models
    rateData    the 41-height sweep

  Then it renders the lab write-up, top to bottom:
    title block -> Aim (answer + red tick if Euler matches exact to
    3 s.f.) -> Set-up (cross-section + controls) -> Results table ->
    Graphs -> Does the model of Vulcan matter? -> Working.

  The handwritten notes under some graphs (velocityNote, accelNote) are
  only shown when they are true for the current settings. With drag on
  they're hidden, because what drag does depends on your airDensity choice.


5. THE ANIMATION (src/components/CrossSection.tsx)
--------------------------------------------------
  simTime = how far into the fall we are (seconds of simulated time).

  Playing: requestAnimationFrame calls a function about 60 times a second.
  Each call measures how much real time passed and adds
      real seconds × playback speed (e.g. 100×)
  to simTime. It stops at the end time.

  sampleAt(samples, t) finds the two saved samples either side of t
  (binary search) and blends between them (linear interpolation), so the
  probe moves smoothly even though samples are 1 s apart.

  Drawing: one scale factor turns metres into SVG pixels, chosen so the
  release point and the bottom of the planet both fit. yOf(r) converts a
  distance from the centre into a y position. The depth ruler on the
  right uses the SAME scale, so the probe and its arrow on the ruler are
  always level. Ruler tick spacing (500, 1000, 2000 ... km) is picked so
  there are at most about 8 labels.

  The scrubber slider sets simTime directly (and pauses). When any input
  changes, the animation resets to t = 0.


6. THE GRAPHS (src/components/Charts.tsx)
-----------------------------------------
  One <Chart> component is reused for all eight graphs. It wraps Recharts:
    LineChart + XAxis/YAxis   labelled axes with units
    Line (one per series)     each series has its OWN data array, so lines
                              with different end times share one x-axis
    ReferenceLine (marker)    red "surface" line at the crossing time
    ReferenceArea (rock)      pencil hatching for "inside the rock"
    ReferenceDot (dot)        red circle for "this drop" on the rate graph
    Tooltip                   hover values, rounded to 3 s.f.

  The look: the title is handwritten above a white "printout" with tape
  on it (CSS .taped), axes use plain printer type, and annotations use
  the handwriting font in red pen, as if added after printing. tilt
  rotates each printout by under a degree so they don't look machine-made.


7. LOOK AND FEEL (globals.css, theme.ts, fonts.ts)
--------------------------------------------------
  The page is styled as a student's lab notebook:
    - engineering-paper background: two sets of CSS gradient lines, 20 px
      squares with a darker line every 100 px;
    - Kalam handwriting font (bundled at build time by next/font, so it
      works on a static site);
    - blue ballpoint for the uniform model, green pen for the dense core,
      red pen only for the probe and the surface line;
    - yellow highlighter on the answers;
    - buttons drawn as wobbly hand-drawn boxes (uneven border-radius).
  theme.ts repeats the colours as plain hex codes because SVG attributes
  in the graphs can't read CSS variables.


8. BUILDING AND DEPLOYING
-------------------------
  next.config.ts: output: "export" makes `npm run build` produce a plain
  folder of HTML/JS/CSS in ./out, with no server needed. basePath
  is needed on GitHub Pages because the site lives at
  username.github.io/REPO-NAME/; the workflow sets it, while Vercel
  leaves it empty.

  deploy.yml: on every push to main, GitHub installs the packages, runs
  `npm run verify` (stops if the answers are wrong), builds, and
  publishes ./out to GitHub Pages.

  Commands:
    npm run dev      live-reloading site at http://localhost:3000
    npm run verify   prints PASS/FAIL for 1.36e3 s and 5.15e6 Vulcans/s
    npm run build    makes the static site in ./out


9. THE INTERACTIONS (and where the ideas came from)
---------------------------------------------------
  Drag-to-change numbers (Scrub.tsx). The drop height and launch speed in
    the Aim sentence are "scrubbable": press and drag sideways. Each pixel
    is one step (50 km or 50 m/s). Pointer capture keeps the drag going
    even if the mouse leaves the number. Arrow keys work when it's focused
    (Shift = 10 steps). Idea from Bret Victor's Tangle "reactive documents"
    and Red Blob Games.

  Click-to-toggle words (WordToggle in Lab.tsx). "the same density all
    the way through" / "ignoring air" flip the interior model and drag.
    They're <span role="button"> rather than <button> because Chrome
    won't let a button wrap across two lines.

  Guess first (Lab.tsx, markGuess). Type a guess in seconds and it gets
    marked in red pen: within 5 % is a tick, otherwise "x % too long/
    short". Making a prediction before seeing the answer helps you
    remember it (the NYT "You Draw It" idea).

  Linked graphs (timeline.ts + Charts.tsx + CrossSection.tsx).
    timeline.ts holds three numbers: time (where the animation is),
    hover (the time under your pointer on a graph) and end. It is NOT
    React state on purpose: it changes 60 times a second while the probe
    falls, and putting it in Lab would redraw all eight graphs every
    frame. Instead, only the parts that care subscribe to it:
      - CrossSection draws the probe at `time` and a dashed pencil
        "ghost" probe at `hover`; the readout follows your pointer.
      - Each time graph has an overlay of three absolutely positioned
        divs (a red "now" line, a dashed hover line, and a white "cover"
        that fades the part of the graph the probe hasn't reached yet, so
        the graph traces itself as it falls). They're moved with
        transform: translateX(...%). That's cheap for the browser and never
        re-renders Recharts.
      - The g-vs-r graph uses followX to turn the time into the probe's
        distance from the centre, so a red line slides along r as it falls.
    The overlay has to line up with Recharts' plot area, so Charts.tsx
    keeps the plot insets in one PLOT constant (chart margins + axis
    sizes). If you change the margins, change PLOT too.

  Pencil ghost of the previous run (Lab.tsx). After you change a
    setting, the velocity graph keeps your previous run as a dashed
    pencil line. useSettled waits until you've stopped dragging for
    350 ms, so the ghost is the last setting you actually stopped on,
    not one from a split second ago.

  Keyboard (CrossSection.tsx). Space = drop / pause, left/right arrows
    = step 1 % through the fall (Shift = 10 %), R = reset. Ignored while
    you're typing or using a control.

  Motion. Only one thing really animates: the yellow highlighter swipes
    across the answer, left to right, when it settles on a new value
    (the <p> is re-keyed so the CSS animation re-runs). Everything else is
    a 120 ms colour or opacity change. With "reduce motion" switched on
    in your system settings, the swipe is turned off.


10. COMMON CHANGES
-----------------
  Change a given value (radius, g0, population) .. top of physics.ts
  Change the probe size .......................... PROBE_RADIUS, physics.ts
  Change the time step ........................... DT, physics.ts
  Change slider ranges ........................... the <input type="range">
                                                   lines in Lab.tsx
  Change colours ................................. :root in globals.css AND
                                                   theme.ts
  Add a graph .................................... another <Chart ... /> in
                                                   Lab.tsx
